# Corrections de sécurité ForSure et ordre de mise en service

Les lots des 18–22 octobre 2026 corrigent d’abord les paiements et les actions privilégiées, puis les frontières sociales et IA. Ils sont préparés dans le workspace, sans fusion, push, migration Cloud ni publication. Le serveur Aegis, les clés des utilisateurs, le registre des appareils et le protocole Libsignal ne sont pas modifiés. Ces correctifs locaux ne clôturent pas l’ensemble de l’audit en production. L’ordre actuel est de terminer les vérifications sans déployer.

R2 est reporté à la demande de l’utilisateur. Les changements R2 déjà présents dans le workspace sont conservés, mais aucun nouveau correctif ni déploiement R2 ne fait partie de cette reprise.

## Autorité des actions Zeus

Le modèle conserve la capacité de proposer un ajustement du feed, mais l’outil `update_algorithm_config` n’écrit plus en base. Seule l’action administrative `apply_proposal`, envoyée par le bouton de validation, appelle `apply_admin_feed_config_update`. Cette transaction vérifie le rôle actuel, valide les champs et types existants, refuse une configuration modifiée entre lecture et écriture, puis enregistre ensemble le changement et son audit privé. Une action inconnue n’obtient plus un faux succès. L’interface attend `success:true` et `applied:true` et bloque les doubles clics en cours de requête. Aucun SDK ni fournisseur IA n’est remplacé.

Pour une publication ou un commentaire existant, le navigateur fournit l’identifiant : Zeus relit l’auteur, le texte et le rattachement enregistrés. Un texte navigateur différent ne remplace pas la preuve. `apply_owned_content_moderation` revérifie cette révision sous verrou après l’appel IA, puis enregistre ensemble avertissement, réponse système éventuelle, alerte éventuelle et reçu privé. Un retry renvoie le verdict initial sans accumuler d’avertissements ou de commentaires. Une erreur d’écriture ou de résultat IA ne devient pas un faux succès. Les brouillons restent consultatifs et ne créent pas de sanction.

Les clients ne peuvent plus choisir `is_zeus_reply:true`, changer l’identité ou déplacer un commentaire. Les réponses restent liées à la publication de leur parent. Les utilisateurs conservent l’édition de leur texte et l’acquittement de leurs avertissements ; les modérateurs conservent la revue des alertes. Le préflight signale les anciennes lignes suspectes sans les réécrire.

Ce circuit reste déclenché par les callbacks du client : il n’impose pas une modération serveur à toutes les publications. Une file ou un déclencheur serveur vérifié serait un lot distinct. La vérification d’image n’est pas implémentée ici ; les réponses texte l’indiquent explicitement. Aucun contenu de la messagerie E2EE ne passe dans ce circuit.

Exécuter `supabase/checks/security_fix_preflight_20261018.sql` dans le projet ForSure. C’est une vérification en lecture seule. Les tables de clubs existent dans les types Cloud mais leur création n’apparaît pas dans l’historique local ; une application aveugle de toutes les migrations sur une nouvelle base n’est pas certifiée.

Vérifier le catalogue Stripe réel : le prix Créateur courant est `price_1UOT8Q6wgOEGAgcGDX1iQ2Lt`, 499 centimes EUR par mois. Un éventuel `STRIPE_CREATOR_PRICE_ID` est une configuration serveur, pas un choix du navigateur. Ne pas remplacer le prix sans vérifier la compatibilité des abonnements existants.

Contrôler les anciennes commandes et négociations déjà déclarées acceptées/payées avant le durcissement. Elles ne sont ni supprimées ni arbitrairement réécrites. Une commande historique sans session Stripe ou PaymentIntent prouvable n’est pas confirmée payée par le nouveau vérificateur. Une incohérence de stock après capture de paiement exige une réconciliation/remboursement supervisé ; aucun faux succès n’est renvoyé.

Exécuter les advisors de sécurité Cloud et exporter les privilèges avant/après. Aucune preuve de droits en production ne doit être déduite uniquement des tests PGlite.

Inspecter les contraintes et triggers de suppression Auth dans le préflight. `admin-delete-user` ne supprime plus manuellement des lignes pour contourner une contrainte : si Auth refuse, l’administration doit réconcilier la dépendance. Les données sans cascade, les obligations de rétention et les fichiers externes nécessitent un workflow séparé. Pour la transparence, obtenir par un canal indépendant la clé publique Ed25519 de l’autorité existante et son identifiant. Configurer `VITE_KT_PUBLIC_KEYS` sous la forme `{"identifiant":{"kty":"OKP","crv":"Ed25519","x":"clé-publique-base64url"}}`. Aucun `d`, secret ou jeton n’est attendu. Ne pas prendre une clé en base et la déclarer fiable parce que le serveur audité la fournit. Sans cette configuration, l’audit affiche explicitement une autorité inconnue. Contrôler les anciens lots incomplets signalés par le préflight ; aucun n’est supprimé ou re-signé automatiquement.

## Régression sûre

Chaque migration est transactionnelle. Les tests provoquent notamment un manque de stock : reçu, statut, notification et panier restent inchangés si la transaction échoue. Les changements ne suppriment ni messages, ni appareils, ni clés.

Ne pas revenir aux anciens droits financiers ou aux colonnes publiques pour résoudre une régression. Avant chaque phase, conserver un export de schéma/privilèges et une sauvegarde vérifiée. Si un écran régresse, conserver les refus serveur et corriger/revenir à un client compatible ; suspendre uniquement l’action concernée si nécessaire. Après la phase 6, un ancien client à sélection globale n’est pas un retour arrière compatible.

Ne pas retirer les nouvelles colonnes/RPC pendant que les nouvelles fonctions les utilisent. Les restaurations cryptographiques ou une réouverture globale des droits ne constituent jamais un retour arrière acceptable.

Conserver les garde-fous et RPC Zeus en cas de retour à une interface compatible. L’ancien gestionnaire autorisant le modèle à écrire ou utilisant les preuves du navigateur n’est pas un retour arrière sûr. En cas de panne, garder un refus explicite de l’action concernée ; ne pas annoncer une modération ou une application réussie. Ne pas purger les reçus sans stratégie de rétention et d’anti-rejeu pour les anciennes tentatives.

En cas d’indisponibilité du quota, rétablir son RPC et ses privilèges ; ne pas réactiver le succès de secours. Le refus temporaire concerne l’action protégée, sans effacer de clé ni révoquer un appareil. Les réservations IA interrompues par un crash restent comptabilisées pour la journée UTC : aucun remboursement aveugle ne permet de contourner le quota après un appel fournisseur au résultat inconnu. Une politique de rétention des anciennes réservations reste à configurer sans toucher au jour courant.

Les anciennes commandes doivent être réconciliées avec Stripe avant une nouvelle expédition, car le statut textuel « payé » seul ne suffit plus. Une réservation transporteur n’expire pas automatiquement : un timeout peut masquer une étiquette déjà créée. Le support doit rechercher le résultat chez le transporteur et vérifier la commande avant toute reprise supervisée. Aucun bouton client ni tâche automatique ne remet une réservation incertaine à zéro. Cela évite les doubles créations mais ne fournit pas une garantie de succès « exactement une fois » d’un service externe. Un refus explicite du transporteur demande également une revue avant réessai.

Le nettoyage des comptes reste en inventaire uniquement. L’API de suppression Auth n’offre pas de précondition atomique « toujours non confirmé » : une vérification juste avant la suppression n’élimine pas la course avec le lien du mail. Ne pas réactiver l’ancien effacement profil/compte comme retour arrière.

- Tests du serveur Aegis : **37 réussis** ; parcours Libsignal avec le vrai WASM : six directions entre trois identités, incluant rejeu, retard, renouvellement et substitution.

Les avertissements de taille de chunks, PostCSS, flatDir et versions des outils SDK ne constituent pas une validation de performance ou d’appareils physiques. - Les tests Python/DB-IP et les sockets localhost des tests Aegis nécessitent l’accès normal aux dossiers temporaires et au réseau local Windows : ils passent après relance avec ces permissions, sans suppression ni affaiblissement de test.
- Le contrôle des en-têtes réellement servis reste rouge : HTTP 200 mais CSP anti-iframe et X-Frame-Options absents. C’est un point ouvert côté hébergement, pas un échec dissimulé de la suite locale. Aucun déploiement n’a été effectué pour le modifier.

Ces résultats ne couvrent pas un paiement Stripe réel, les migrations dans Lovable Cloud, R2 ni une validation sur appareils physiques. Un binaire Deno 2.5.3 disponible dans le cache npm a permis le test MCP réel ; les autres gestionnaires ne sont pas certifiés sur le runtime Cloud par leur seule transpilation locale. Les mises à jour npm ont été installées avec la chaîne de confiance Windows ; aucun manifeste privé n’a été envoyé à un audit npm distant. Toute modification ultérieure impose de relancer les contrôles concernés avant fusion.
